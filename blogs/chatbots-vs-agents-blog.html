Build vs. Buy Clarity

AI Chatbots vs. AI Agents.
Stop Conflating Them.

Everyone is calling their AI chatbot an "AI agent" now. It's almost never true. The difference isn't the model. It's what happens when the user stops typing.

For engineers evaluating AI products 6 min read April 2026

I built a real AI agent platform last month. Each user gets their own AI agent backed by a dedicated cloud server. You tell it what you want done. It writes code, runs commands, evaluates results, and comes back with an answer. Not a response. An answer.

I spent the first day confused about why this felt so different from every AI chatbot I'd ever built. Same models. Similar prompts. The conversation felt different. The capability felt different. The product felt different.

Then it clicked. The thing I'd built wasn't a better AI chatbot. It was a different category of software.

Here is the distinction the industry keeps getting wrong:

Category 1
AI Chatbot
A UI pattern. A conversation.
  • User types — bot responds — conversation ends
  • System goes idle when user stops typing
  • One turn of work per user message
  • Returns a response, in text
  • No autonomy outside the chat window
Category 2
AI Agent
A runtime. A process.
  • User states outcome — agent works until done
  • Continues working when user closes the tab
  • Calls tools, reads state, takes actions
  • Returns a result: a built thing, a completed task
  • Has autonomy bounded by permissions, not chat turns

That's the line. Not the technology underneath. The autonomy after the user stops typing.

So When Should You Actually Build One?

The runtime distinction tells you what category a product belongs to. It doesn't tell you whether you need an agent for the thing you're trying to do. Most things still don't need one.

The cleanest filter I've seen for this question is a three-letter test from a piece by executive coach Sangeet Paul Choudary on the practical use of agents. He calls it ARR:

Framework The ARR Test: When an Agent Makes Sense
A Autonomous
Can the work happen without your input during execution? If every step needs human approval, an agent is overkill. You want a workflow with checkpoints, not autonomous action.
R Recurring
Does this task happen more than once? One-off tasks rarely justify the setup cost. Weekly reports, daily triage, every-deploy validation. These compound. Agents earn their keep on repetition.
R Reviewable
Can you tell after the fact whether the agent did a good job? If you can't define what "done correctly" looks like, you can't trust an autonomous system to produce it. Reviewability is the safety rail.

If your task is all three (autonomous, recurring, reviewable), it's a strong candidate for an agent. If it needs live judgment, only happens once, or can't be clearly evaluated, you want a better prompt or a workflow, not an agent.

This is the filter that prevents the most common failure mode of 2026: building agents for things that should have been a Slack reminder.

The Same Model, Two Different Categories

Claude Opus 4.7 powering a chatbot is still a chatbot. GPT-5 wrapped around a support ticketing tool is still a chatbot. The model doesn't determine the category. The runtime does.

Customer support bots, the chat tab in your SaaS dashboard, "AI assistants" that answer questions inside documentation sites, ChatGPT in a browser tab: all AI chatbots. Useful. Sophisticated. Valuable. But the work stops when you stop typing.

Compare what an actual agent looks like in practice:

Same prompt, two different products
User: "Find why my last deploy failed and fix it"
AI Chatbot
"Based on common deployment failures, you should check your CI logs for errors, verify environment variables, and ensure your build artifacts are correct. Would you like me to walk you through these steps?"
AI Agent
[Reads CI logs for the failed deploy. Identifies the failing test. Pulls the relevant code file. Runs the test locally. Identifies the type mismatch. Edits the fix. Re-runs the test. Commits the fix on a new branch. Opens a PR with a summary of the change.] "Done. The deploy failed because of a type mismatch in the user serializer. Fixed it on branch fix/user-serializer-types and opened PR #847 for you to review."

Notice what's missing in the second one. No follow-up questions. No "would you like me to." No menu of options. The agent had a clear outcome to deliver, the tools to deliver it, and the autonomy to use them.

"An AI chatbot answers your question. An AI agent achieves your outcome. That's not a feature upgrade. It's a different category of software."

Why The Marketing Got So Confused

Look at how products positioned themselves in 2023–2024. Then look at how the same products position themselves now.

2023 marketing

"Our AI chatbot helps customers find answers instantly."

2025 marketing

"Our AI agent autonomously resolves customer queries."

Same product. Different label. The underlying software didn't change. It just got renamed because "agent" sounds more powerful than "chatbot." Investors fund agents. Engineers want to build agents. Customers want to buy agents. So everything became an agent.

The problem with this isn't pedantic. It's that when you're evaluating tools for your team or your stack, you need to know what you're actually getting. A "customer support agent" that requires a human to approve every action, ask every follow-up question, and chase every loose end isn't an agent. It's an AI chatbot with a marketing budget.

Two Tests, Five Seconds Each

When someone tells you their product is an agent, you don't need to read the docs. You don't need to test the API. Two questions narrow the field.

Test 1: The autonomy test.

"Can it complete a task while I'm not watching?"

If yes, it's an agent. If it has to ask you something before every meaningful action, or the work stops the moment you stop typing. It's an AI chatbot.

That filters out the products mislabeling themselves. But it doesn't tell you whether the remaining agents are actually good. Plenty of real agents are still rigid scripts wrapped in a chat interface. They work when everything goes right and break the moment reality changes. For that, you need a second test.

In the 1970s, Air Force Colonel John Boyd was trying to understand why American F-86 pilots in the Korean War kept beating the technically superior Soviet MiG-15. The MiG was faster and climbed higher. It should have won. It didn't.

Boyd's answer: the F-86 cockpit gave pilots better visibility and faster controls, which meant they could see, decide, and act faster than the enemy could respond. He called this loop OODA: Observe, Orient, Decide, Act. The pilot who completed the loop fastest won, even with worse equipment.

The OODA loop is also the right test for whether something is actually an agent rather than a fancy workflow:

Test 2: The OODA test.

"When the obvious path fails, can it choose a better one?"

A workflow follows the script. An agent observes that the script didn't work, orients to the new situation, decides on a different approach, and acts again. If a system can only follow the path you originally planned, it's automation. If it can find a new path when the first one breaks, it's an agent.

Concrete example: every Friday an automation checks grocery prices, builds a shopping list, and places an order. Works fine for months. Then one week your usual rice is out of stock and you have six friends coming for dinner on Saturday. A workflow either fails silently or orders what it can. An agent notices the missing item, finds a substitute, scales the quantities up for six people, checks your calendar, sees the dinner, and rebuilds the order around the actual situation.

That second behavior is what the autonomy test alone won't catch. Apply both tests in sequence: autonomy first, then OODA. That narrows the field to products doing genuinely different work.

The Architecture Difference

The difference is concrete and worth understanding. An AI chatbot is a request/response cycle. The architecture looks like:

Frontend sends a message. Backend calls the model. Model returns text. Backend returns text. Frontend renders. Done. The system holds no memory between your messages. Even when there's session history, the system isn't doing work. It's waiting.

An agent is a long-running process. The architecture looks more like:

Frontend sends an outcome. Backend starts a process. Process reasons about the goal, calls tools, evaluates results, calls more tools, corrects course, runs commands, reads files, writes files, makes decisions. The process is still running when the user closes their browser. The work continues. State persists. The system isn't waiting for the user. It's working for them.

The "calls tools" part is where the rubber meets the road. In 2026, most modern agents do this through Model Context Protocol, an open standard from Anthropic that lets models call into GitHub, file systems, databases, browsers, and any other service through a uniform interface. MCP is the reason agents can suddenly do real work without being hardcoded to specific APIs. If you're evaluating something that calls itself an agent and it doesn't use MCP or a similar tool-protocol, ask how it actually integrates with the systems it claims to operate. The answer matters.

That's why building an agent is harder than building an AI chatbot. You're not building a conversation. You're building a runtime. You need the system to remember what it's doing between steps, handle errors on its own, give you visibility into actions you didn't trigger manually, and stay secure while doing real work on real systems.

What This Means For Engineers

If you're choosing tools: when a product says "AI agent," apply both tests: autonomy first, then OODA. Most won't pass either. The ones that pass both are about to become important parts of how you build and ship software.

If you're building products: don't call your AI chatbot an agent. The bar is rising. Customers, technical evaluators, and increasingly investors are learning the difference. Mislabeling a chatbot as an agent worked in 2024. It's getting harder in 2026.

If you're a senior engineer thinking about where the work is going: the AI chatbot space is crowded and mature. The agent category is less crowded right now, but that window is closing fast. The companies that figure out how to build reliable, focused agents that businesses can trust with real workflows will shape the next several years of software.

One More Thing

The reason this distinction matters to me personally: I spent a week building AXON, a platform where every user gets a real AI agent backed by a dedicated cloud server. The agent writes code, runs it, edits files, and streams results back. No questions unless it genuinely needs them.

By day three I understood why this felt different from every AI chatbot I'd ever built. By day five I understood why most of what's being called an agent isn't one. By day seven I understood why this distinction is the one engineers should be paying attention to right now.

The model is not the product. The runtime is the product. And the runtime is where the most interesting software of the next few years is being built.
